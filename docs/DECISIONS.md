# Telemachus Decision Register

> Index over architectural decisions. The full rationale for each ADR lives in [docs/runtime_decisions.md](runtime_decisions.md) — this table is a lookup, not a replacement. Implementation-level decisions made while building the Runtime Lifecycle milestone are recorded separately below, since they aren't formal ADRs but are now load-bearing facts about the codebase.

## Approved Decisions (ADRs, `docs/runtime_decisions.md`)

| ID | Decision | Status | Rationale (compressed) | Implemented? |
|---|---|---|---|---|
| ADR-001 | Runtime and Core Separation — Runtime coordinates, Core reasons | Approved | Reasoning should stay deterministic and independent of operational concerns | **Yes** — enforced by `tests/test_runtime_boundaries.py` |
| ADR-002 | Recovery-First Lifecycle — every startup is a recovery; initialization happens once, at installation | Approved | Telemachus is a persistent system, not a repeatedly-launched app | **Yes** — `LifecycleState` transition table structurally forbids skipping `RECOVERY`; `installed_at` is written once and never rewritten |
| ADR-003 | Universal Observation Model — normalize all external signals into one Observation type | Approved | Lets the Core reason independently of external integrations | Partially — the `Observation` type exists (`runtime/observations.py`) and the Event Loop accepts it; the only production source is the startup Recovery Briefing (`wiring.build_recovery_observation()`). No external signals, plugins or Signal Processor exist, so nothing is yet normalized from outside the process |
| ADR-004 | Immutable Observations — facts vs. interpretation stay separate | Approved | Reality is immutable; interpretation is adaptive | **Yes** — `Observation` is a frozen dataclass; mutable state lives on the separate `ProcessingContext`; `tests/test_runtime_observations.py` covers immutability |
| ADR-005 | Semantic Readiness — invoke the Core when meaningful, not on a timer | Approved | Avoid unnecessary reasoning cycles | Partially — `EventLoop.tick()` invokes the Core only when an Observation is queued (an empty queue invokes nothing), and `RuntimeLifecycle._tick_event_loop()` only ticks a non-empty queue. This is structural readiness only; semantic readiness is not implemented. Timeouts are not used as a reasoning trigger |
| ADR-006 | Plugin Isolation — plugins translate to Observations, stay isolated from Core | Approved | Stable Core architecture, independent plugin evolution | **No** — no plugin system exists |
| ADR-007 | Resource-Based Concurrency — schedule resource ownership, not threads | Approved | Correctness over raw throughput | **No** — no resource scheduler exists. The Event Loop is single-threaded and main-thread, and the pipeline is synchronous |
| ADR-008 | Adaptive Runtime Regulation — the Runtime regulates conditions, never reasons | Approved | Keep the Event Loop non-cognitive | Partially — the Lifecycle state machine itself performs no reasoning (consistent with the principle), but the Event Loop (`runtime/event_loop.py`) also performs no reasoning and only decides whether and when to invoke the Core through an opaque callable. The regulating behavior it describes (load-based backpressure, Runtime modes) doesn't exist yet; the only overflow behavior is rejecting the newest Observation when the 1000-item queue is full |
| ADR-009 | Graceful Degradation — aggregate/batch/delay/throttle before discarding | Approved | Resilience over catastrophic failure | Partially — the LLM router's fall-through/cooldown design follows this principle, but the router itself is unwired; Runtime shutdown degrades independently per resource (memory store failing to close doesn't block the rest of shutdown) |
| ADR-010 | Immutable Architectural History — accepted ADRs are never rewritten, only superseded | Approved | Preserve architectural intent over time | Process decision, not a code decision — followed by not editing this file's ADR table content, only adding to it |

## Implementation Decisions (Runtime Lifecycle milestone, not formal ADRs)

These are real, load-bearing facts about the current codebase. They resolve ambiguity ADR-001/002 left open at the implementation level.

| Decision | Status | Rationale | Source |
|---|---|---|---|
| Runtime persists to a **separate `runtime.db`**, never into `telemachus.db` | **Existing** (implemented) | Crash detection must not depend on Core memory-store health; a shared file made a leaked handle able to silently reintroduce unclosed-WAL bugs | `src/telemachus/runtime/state_store.py` |
| `BootstrapProtocol` gained an **additive, optional** `first_awakening` parameter (type `bool` or `None`, defaulting to `None`); every existing caller is unaffected | **Existing** (implemented) | The Runtime knows whether an installation is new; the Core config only grants *permission* for first awakening — neither should silently override the other | `src/telemachus/bootstrap.py`; preserves all 44 pre-existing bootstrap tests unmodified |
| First awakening triggers only when **both** are true: this is a new Runtime installation, and `config.bootstrap.first_awakening` is `true` | **Existing** (implemented) | Fixes a real defect: previously, `first_awakening = true` in config caused *every* startup to re-trigger first awakening, forever | `runtime/lifecycle.py: start()` |
| The five bootstrap phases are invoked as **one indivisible unit** inside the Runtime's `RECOVERY` state; the Runtime never reorders, splits, or inspects phase-level data — only `result.success` | **Existing** (implemented) | `codex/bootstrap/BOOTSTRAP_PROTOCOL.md`: "Each stage should complete before the next begins" | `runtime/lifecycle.py: start()` |
| The Lifecycle transition table (`runtime/states.py`) is the **single source of truth** for what state changes are legal; every transition — including inside `shutdown()` — goes through it | **Existing** (implemented) | Makes ADR-002's "no skipping Recovery" guarantee structural, not conventional | Enforced by `InvalidTransitionError`; verified by exhaustive tests over every legal and illegal state pair |
| Signal handlers do the minimum possible work (record + set an `Event` + return); no I/O or database writes occur inside a handler | **Existing** (implemented) | Matches the milestone's explicit requirement and avoids re-entrancy hazards on a second signal | `runtime/signals.py` |

## Later Implementation Decisions (Codex authority through Observation provenance, not formal ADRs)

Facts about the current codebase established by later milestones. They are recorded here with their sources; they do not amend the ADRs above.

| Decision | Status | Rationale | Source |
|---|---|---|---|
| The Codex is the normative source of the Constitution's Protected Constraints: exactly five, parsed from `codex/philosophy/CONSTITUTION.md` | **Existing** (implemented) | Resolves the earlier "Codex is not parsed" gap; a present but malformed document fails Bootstrap, a missing one falls back to the Python default | `core/codex.py`, `core/constitution.py: create_constitution_from_codex()`, `bootstrap.py` |
| Constitutional validation runs in Stage 6 before the autonomy gate | **Existing** (implemented) | Codex hierarchy: Constitution first | `core/constitution.py: validate_action()`, `pipeline.py` |
| Effective constitutional impact of an action is `ActionRequest.affects` ∪ `Tool.protected_constraints` | **Existing** (implemented) | A caller cannot shrink impact by omission. Tool declarations are typed but **not verified** against `execute()` | `tools/base.py`, `pipeline.py` |
| The Runtime does not read the Codex or name the Constitution, and does not import `pipeline`, `wiring` or `tools`; the Event Loop reaches the Core only through an opaque invoker built in `wiring.py` | **Existing** (implemented) | Runtime coordinates, Core decides (ADR-001) | `tests/test_runtime_boundaries.py`, `wiring.build_observation_invoker()` |
| The Event Loop is single-threaded, main-thread and tick-driven, driven from `RuntimeLifecycle.wait_for_shutdown_request()` (one tick per second, one Observation per tick) | **Existing** (implemented) | Both SQLite stores keep default thread affinity and the Core is synchronous | `runtime/event_loop.py`, `runtime/lifecycle.py` |
| Event Loop queue: in memory only, bounded at 1000, highest priority first, FIFO within a priority, newest rejected on overflow; an Observation that fails during dispatch is marked `FAILED` and does not stop the loop | **Existing** (implemented) | No second persistence architecture; reconciliation, not replay | `runtime/event_loop.py` |
| Every Recovery Observation uses `Priority.NORMAL` regardless of termination classification; the classification is preserved in the payload | **Existing** (implemented) | The Runtime does not decide that an unclean shutdown outranks a clean one | `wiring.build_recovery_observation()` |
| The Event Loop creates no `ActionRequest` and executes no tool; every Observation ends at Stage 6 as `NO_ACTION` | **Existing** (implemented) | Authority questions for autonomous action are unresolved (see Q8–Q12) | `wiring.build_observation_invoker()`, `tests/test_runtime_boundaries.py` |
| `PipelineTrace.observation` (`ObservationProvenance`: `observation_id`, `observation_type`, `source`) records which Observation drove a pipeline run; runs not driven by an Observation record none | **Existing** (implemented) | Traceability from execution back to the Observation | `core/types.py`, `pipeline.py`, `tests/test_observation_provenance.py` |
| Synchronous CLI chat does not use the Event Loop | **Existing** (implemented) | Chat answers in-turn; routing it through a queue would change its latency contract | `interaction/cli_chat.py` |

## Open Questions / Unresolved Issues

Not established in repository. Do not silently resolve these — surface them if they become relevant.

| # | Issue | Notes |
|---|---|---|
| Q1 | `docs/lifecycle.md` lists **Installation** and **First Initialization** as separate steps but never defines the difference. The implementation collapsed them into one `INSTALLING` state. | If they're meant to differ, the state model needs a second state. |
| Q2 | ADR-002 permits a user-triggered reset ("unless the user explicitly resets the system") but specifies no reset mechanism. | Currently the de facto reset is deleting `runtime.db` by hand. No command exists for this. |
| Q3 | `FIRST_AWAKENING.md` defines completion as reaching sufficient *understanding*, not as a boolean flag — but no persistence mechanism for "understanding is complete" exists anywhere. | The Runtime resolves only "is this a new installation," not "has awakening concluded." These are treated as genuinely distinct, unresolved concepts. |
| Q4 | **No single-instance guard.** Two Runtime processes sharing one `data_dir` will each treat the other's open session as a crash. | Flagged as the sharpest correctness gap left by this milestone. |
| Q5 | **Resolved in part.** Asked whether Codex markdown is meant to be parsed at runtime. The Codex Authority Layer answers this for the Constitution: Protected Constraints, the First Memory and the scoped Identity fields are loaded from the Codex (`core/codex.py`, `bootstrap.py`). Residual: the Core Principles list in `create_constitution_from_codex()` is still the Python factory's list, and `create_default_constitution()`/`create_default_identity()` remain as fallbacks when a Codex document is missing. | Whether those remaining Python-defined values should also come from the Codex is not decided here. |
| Q6 | Interactive `chat`'s Ctrl+C behavior changed: the Runtime's signal handler intercepts SIGINT before Python's default `KeyboardInterrupt` can, and since the handler never raises, it cannot unblock a synchronous `input()` call the REPL is waiting on. | The memory store still closes correctly (via a `finally` block), but Ctrl+C no longer interrupts an in-progress prompt the way it did before this milestone. Not resolved; documented as a known regression, not fixed, since a proper fix is Event-Loop-shaped work. |
| Q7 | Whether real OS-delivered Ctrl+C reaches the Runtime's installed handler in the actual deployment environment could not be verified in the environment used to build this milestone (isolated to a console-attachment limitation of that specific harness via a minimal, non-Telemachus repro). | The handler *contract* is fully tested (Event set → graceful shutdown completes); only genuine OS signal delivery is unverified here. |
| Q8 | Who may create an `ActionRequest`. No production code does today. | Deferred to a later architecture/design milestone. |
| Q9 | Who is authoritative for `ActionRequest.human_authorized`. It is currently set by whoever constructs the request, and `Constitution.validate_action()` returns `PERMITTED` when it is true. | Deferred. |
| Q10 | How producer-declared `ActionRequest.affects` and tool-declared `protected_constraints` should ultimately be trusted or verified. Today they are type-checked, not verified against behaviour. | Deferred. |
| Q11 | Redesign of `AutonomyCharter.check_initiative()`: it has no production caller and decides by free-text substring matching. | Deferred. |
| Q12 | The autonomy domain for Runtime-originated Observations is undefined (the autonomy stage falls back to `"research"`), and Observations enter the pipeline as user-input-shaped text. Also deferred: autonomous `ActionRequest` generation, the ACTIVE/AUTONOMOUS tool architecture, and the later Event Loop semantic stages (Signal Processor, Aggregation, dynamic priority, dependency/resource scheduling). | Deferred. |
